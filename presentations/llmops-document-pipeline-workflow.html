The problem

At 100k docs/day, "mostly works" is a production incident

A document pipeline isn't a queue of independent jobs -- it's a state machine under concurrency, and most of the hard bugs live exactly at the seams a simple retry loop can't see.

Scatter-gather is a hazardA sharded document's last shard can commit while another replica is still mid-write -- a naive SELECT count(*) join can miss or double-fire.
Retries divergeA redelivered message and its retry can both reach "complete" with different extracted values -- something has to decide, structurally, which one wins.
Lost work hides quietlyA crashed worker mid-extraction leaves a document silently stuck -- nothing fails loudly, it just never finishes.
A model can lie convincinglyPrompt injection or hallucination can produce an answer that looks grounded in the source text but is still arithmetically wrong.

Architecture

How a document actually moves

From an uploaded PDF to a posted, auto-approved record -- every arrow below is a real Kafka topic or a real Postgres transaction, not a conceptual box. Scroll to follow one document through.

01 · The foundation

Ansible + ArgoCD provision everything

Ansible orchestrates the whole deploy; ArgoCD owns every K8s manifest inside the cluster, including the KEDA operator itself. Nothing here is a raw kubectl apply.

02 · Ingest

The orphan detector *is* the ingest path

Locally, fake-gcs-server has no bucket-notification wiring -- so a 10s polling loop that finds new objects under inbox/ is the design doc's own recommended fallback, not a shortcut. Triage classifies and creates the one ledger row.

03 · Fan out, then rejoin

Scatter-gather, without a lost-join hazard

Large scans split into page-range shards that OCR in parallel. The join that detects "all shards done" is a single guarded UPDATE ... RETURNING under the parent row's lock -- the winning shard publishes; it does not reassemble.

04 · Extraction funnel

Cheap model first, gated at every step

Mock/cheap/strong tiers, each result checked by five deterministic gates before anything auto-posts. First-writer-wins on commit -- a redelivered retry can never overwrite an already-committed result.

05 · Watched and self-healing

Lost work gets found automatically

The sweeper, DLQ replay, dead man's switch, and a synthetic canary run continuously underneath everything else. KEDA watches Kafka consumer lag and scales the busiest stages up on its own.

Appendix · A2

The state machine & the scatter-gather join · docpipeline/core/ledger.py

GuaranteeHow it's enforced
transition()A single guarded UPDATE ... WHERE state = ANY(allowed) RETURNING state. Raises IllegalTransition rather than silently no-op'ing — a _running state is only enterable from its own _pending state.
record_shard_and_maybe_join()Inserts the shard with ON CONFLICT DO NOTHING (duplicate deliveries are free no-ops), then UPDATE ... RETURNING shards_done, shards_total under the same row lock — never a separate count query, which is exactly the read that can observe a stale value mid-commit.
commit_extraction_result()First-writer-wins: UPDATE ... WHERE extraction_result IS NULL. A redelivered retry that races an already-committed result loses, deterministically.
pipeline_ro grantsNo INSERT on outbox, no Kafka producer credentials — the operator's read-only replay lane is structurally incapable of writing, not merely a function that happens not to call enqueue().
Source: docpipeline/core/ledger.py · tests/test_state_machine.py · tests/test_scatter_gather_join.py · tests/test_read_only_role.py.
Appendix · A3

Five deterministic quality gates · docpipeline/core/gates.py

GateWhat it catchesOn inconclusive
groundingEvery extracted value appears in the source text — catches hallucination directly, but not a swapped seller/buyer (both genuinely appear in the text).blocks
arithmeticRecomputes the subtotal from line items independently — this is what actually defeats prompt injection, since grounding alone passes an injected-but-present total.blocks
iban_mod97IBAN checksum validation.allows
plausibilityTotal within a sane ceiling; due date within a year of the issue date.n/a (fail/pass only)
business_dedupeCatches a rescanned/re-emailed duplicate — different bytes, same (vendor, invoice_no) — which the content-checksum primary key alone cannot.blocks
applies_to ≠ model output
arithmetic's applies_to is doc_type == "invoice", set by a keyword heuristic at triage time — before extraction ever runs. A model can't evade the gate by simply omitting line_items, because the predicate was already decided before it got a chance to answer.
Source: docpipeline/core/gates.py · tests/test_gates.py · tests/test_extraction_funnel.py (injected_total, swapped_roles, refusal, context_overflow scenarios via a programmable mock model).

What's demo-only — production readiness gaps

This repo optimizes for "every structural hazard is genuinely guarded, on a laptop, for $0" — not "safe to expose publicly" or "safe to auto-promote." These are the deliberate shortcuts, and what closes each one.

AreaThis repo (demo)Needed for production
CI enforcementQuality gates and the read-only/break-glass role split are proven by the test suite and by running live — not gated in CIMake both a first-class CI check, independent of which script invokes the pipeline
Role-assignment gapgrounding passes on a swapped seller/buyer (both genuinely appear in the text); this repo proves the gap exists but doesn't implement the ensemble remediationA second, independent extraction pass or a role-specific consistency check
Cluster lifecyclemake e2e-k8s deletes and rebuilds the entire minikube cluster every run — correct for a clean-room demo, far too slow and destructive for a shared environmentA persistent cluster with proper reconcile-on-drift instead of delete-and-rebuild
